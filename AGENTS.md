# AGENTS.md

Guidance for AI agents and humans working on **Kober** (repository `kober`): a shared shopping list PWA with a game (leaderboard), independent of VG Dresden but using its public product data.

## Language rules

- **Source code is English**: identifiers, comments, test names, error/log messages, config comments, workflow step names.
- **The web app UI is localised**: it follows the system language, German or English (English is the fallback). All user-visible text lives in `public/i18n.js` (`STRINGS.en` and `STRINGS.de`, keys must exist in both). Do not hard-code UI text in `app.js`; static texts in `index.html` have English defaults that `applyStatic()` replaces. Use `t('key', { param })`. Never name a loop variable `t` in `app.js` (it shadows the translation function). `?lang=de|en` overrides the language for testing.
- Documentation: `README.md` is English. `docs/*.md` are currently German and stay German unless asked otherwise. The end-user help page (`public/docs/index.html`) and the privacy notice (`public/privacy.html`) are bilingual and follow the same language detection.
- Data coming from the VG servers (product and deposit names) stays German.
- When telling the maintainer where to click in an external web console (Firebase, Google Cloud, GitHub, Apple, ...), use the **English** names of menus, tabs and buttons exactly as the English interface shows them (for example *Project settings → General → Your apps → Add app*, *Security → Secret scanning → Close as*), even though the conversation is German. The maintainer's consoles are set to English; German translations only cause searching.

## Layout

- `public/` is the whole app (static, ES modules, no build). Served by GitHub Pages.
  - `app.js` UI and flows, `flows.js` the pure logic behind some flows (reset plan, too-long numbers, checkout ticks, VG loader state, first upload; DOM-free so `test/flows.test.js` covers it), `store.js` data layer, `vg.js` VG data/import, `i18n.js` texts, `sw.js` service worker, `legal-config.js` contact for the privacy page.
  - `privacy.html`, `docs/index.html` (help page for end users), `vendor/` (third-party, MIT, excluded from checks).
- Help page screenshots (`public/docs/img/<lang>-<scene>.jpg`) are built **locally and only when the user explicitly asks for it** (not in CI, not automatically after UI changes). The agent runs `npm run docs:screenshots` (`scripts/docs-screenshots.mjs`: `playwright-core` with the installed Chrome or `CHROME_PATH`, the real app in demo mode with Firebase off, invented VG demo data from `scripts/fixtures/vg/`, 375px, German and English). **Every generated image must be looked at (Read tool) before it is committed**: no cut-off or overlapping text, no toast or demo banner, no half-rendered state, the right language, the current UI (new buttons, colours). If something is off, fix the script or the app and render again. `npm run docs:screenshots -- /tmp/shots` previews without touching the repo. **Order of work: screenshots come last.** Implement everything else first (code, texts, docs, tests), commit and push that, and only then render, check and commit the images, followed by a second push. Rendering earlier wastes work because every further UI change makes the images stale again. The images are not refreshed by UI changes on their own: when a change is visible in a screenshot scene, tell the user and offer to regenerate.
- `scripts/` maintenance scripts: `cleanup-lists.mjs` (cleanup of old lists), `make-icons.mjs` (`npm run icons`: draws the app icon, the fox peeking out of a Kober (a woven basket) on the VG green, and renders `public/icon.svg`, `public/logo.svg` and `public/icons/*.png` with Chrome; bump `VERSION` in `public/sw.js` afterwards). `database.rules.json` Firebase Realtime Database rules (**published by hand in the Firebase console**, see `docs/security.md`).
- `test/` Node tests (`node --test`, no dependencies). `docs/` developer and maintainer docs (Markdown, German, not deployed; the end-user help page is `public/docs/`, served with the app).

## Behaviour that must stay true

- **Local first**: the list lives in `localStorage` under the list code `LOCAL` (no name, no server, works offline). The leaderboard/game only exists for shared lists. Sharing uploads the local list (`store.importList`, no points are awarded for existing items) and removes the local copy; the header has share and a "…" menu (share list, the same dialog as the share button; reset list: a dialog with check boxes, open items, items in the basket (default on, named like the list section "In the basket"), empties (default on) and, on shared lists only, "Reset the ranking to 0 (new round)" (default off, `store.resetScores`, the same as the "New round" button of the ranking tab); unticked labels fade, the action button turns red (`--danger`, `.btn.destroy`) while open items are ticked and removing open items still asks once more, with a note that it applies to everyone on a shared list; which store calls run is `resetPlan` in `flows.js`; import list (from the VG app); "Join list" on the local list only; "Leave list" on shared lists only; help; privacy). The ranking tab has "Change name" (name and emoji; `store.renameUser` moves points, empties and marks to the new key). Player emojis (`EMOJIS` in `app.js`) are single code points, because joined sequences render differently across phones. There is no title and no counter in the header, only the logo (`logo.svg`, the fox in the Kober without the green tile) on the left.
- Shared lists can be deleted by any member ("Delete this list for everyone", `store.deleteList`; the rules allow writes at list level only for deleting) and expire after 30 days without activity: `store.js` stamps `activity` (at most hourly; opening or changing counts) and `.github/workflows/cleanup.yml` runs `scripts/cleanup-lists.mjs` weekly (needs the secret `FIREBASE_SERVICE_ACCOUNT`, see `docs/retention.md`). A client that sees its shared list disappear falls back to the local list.
- Scanned codes: VG shelf labels carry the VG number (`vgNumFromCode` in `vg.js`: QR "VG n …", 8 digits starting with 0 or 2 (the GS1 in-store ranges) -> digits 4-7, 13 digits -> first 12); other EANs go to Open Food Facts, and scanned text that is no barcode number (a QR code read by zxing on iOS) is ignored. The row scan button (next to each number field) sets the number or remembers the EAN on that item and asks first if the names differ. Typed numbers are checked the same way (`numberFits` in `app.js`; placeholder products are exempt). `similarNames` in `vg.js` is graded: the best word pair by Dice coefficient of letter pairs must reach `SIMILAR_ENOUGH` (0.75), generic words like "Bio" and colours (rot, grün, weiß …) are ignored, words under four letters must match exactly, so Tomate/Tomaten and Äpfel/Apfel Elstar pass while Apfel/Orange and Apfel/Apfelsaft are questioned. Listed synonyms (`SYNONYM_GROUPS` in `vg.js`, e.g. Porree/Lauch, Möhre/Karotte) count as identical: add a group whenever a shopper's word is questioned although it names the same product. Collective words (`COLLECTIVES`, now only "Brot") match every compound that ends in them, so "Brot" fits any bread while Roggenbrot vs Dinkelbrot stays questioned. A word may sit in one group only (a test checks it, the later group would silently win), and a group must not swallow a different product (Apfel vs Apfelsaft, Salat vs Feldsalat stay questioned). The groups were extended against the whole VG product list (about 7100 real products): vegetable sorts, nut kernels, raisins, jam. A number the database lists as unused ("unbesetzt", `p.placeholder`) is always confirmed before it is accepted, in the input bar, on rows and in the scanner. Opening the scanner, a dialog or a menu first dismisses the keyboard (`dismissKeyboard` in `app.js`). Typing in the manual field of the scanner dialog switches the camera off (`stopCamera`, class `manual` on `#scanner`) and emptying it starts the camera again. The manual field in the scanner dialog takes 1-7 digits (a VG number, with suggestions from 3 digits) or 8-14 digits (a barcode number). Number fields have a visible confirm button because the iPhone number pad has no Return key; the add "+" is disabled (muted) until there is something to submit. The confirm ✓ of the quick "No." field of an open item (`form.quick`) only shows while the field holds a number above zero (class `has`, set on `input`; it is not disabled-muted any more because a ✓ next to an empty field looked like "check off"); Enter submits either way. The quick form has a fixed width, so the field itself absorbs the freed space: the name and the left edge of the field never move while typing. The edit field of an existing number (`data-vgedit`) keeps its ✓ always (empty = remove the number).
- Wording: the reset option and the list section are both "Items in the basket" / "Artikel im Korb"; the checkout group of rows ticked at the till is "Already typed" / "Schon getippt" (not "Done" and not "Abgehakt": in this app "abhaken" means putting an item in the basket). Red is for destructive actions only (`--danger`/`--on-danger` for the filled red button, `--red` for text); filled green stays an ordinary action. In the share dialog "Delete this list for everyone" sits in `.dangerZone` (spacing and a divider) apart from "Send link".
- Leaving a shared list asks with the list code in the text ("Code: 4ALVUE – note it down") so the person can join again; the name screen shown when joining by link or code carries a muted line "You are joining list 4ALVUE" (`#joinNote`, set with `textContent` from the validated code).
- The first share of the local list (`shareLocalList` with `uploadLocalList` in `flows.js`): name and emoji are saved first, the local list is removed only after the shared list is up. When the upload fails (no network, `noDbMsg` wording, busy gives `noDbBusy`) the share dialog opens again with an error line and "Try again" in place of "Share list"; one tap repeats it.
- VG data (`vgLoader`, `createVgLoader` in `flows.js`): loads in the background and never blocks the app. After about 10 s without data (or a failed load) the Empties tab shows "VG data not reachable" with "Try again"; the load is retried by that button, on the `online` event and whenever the Empties tab is opened. Suggestions and number checks stay silently off until data arrives. Only read endpoints are called.
- The input bar takes at most 4 digits as a number (`tooLongNumber`): from the fifth digit on "+" is muted and the suggestion area says "VG numbers have 3 to 4 digits" (no toast after the tap). The scanner's manual field is separate and keeps 8-14 digit barcodes. The camera error text is plain ("Camera not allowed or not available. You can type the number below.").
- Checkout ticks (`checkoutDone`): the rows ticked as typed in at the till are stored per list (`NS + 'checkoutTicks'`, `{code, ts, keys}`), sanitised on load (`sanitizeTicks`), dropped when the list code differs or after 24 h without a change, bounded to 200 keys, and ticks of rows that no longer exist are pruned once the list and the VG data have loaded.
- A VG number typed in the input bar (or a tapped number suggestion) and a scanned code put the item straight into the basket (`addToBasket` in `app.js`: an item with that number already on the list is checked off instead of added twice); names are added as open items. Checkout shows only items with a VG number. Typing three or more digits (numbers) or two or more letters (names) shows a tappable list of matching products (tap = add). Names are de-duplicated and always added without a number; the number can be added or changed on the list (small number under an item, empty field removes it). Placeholder products ("unbesetzt …", "RESERVIERT …", about a fifth of the VG list) are never suggested (`vg.js`), but a fully typed placeholder number is still accepted and the item takes the placeholder title.
- Points: +1 for checking off an item (or entering its VG number in the "No." field) and +1 per empties piece; un-checking or deleting takes the point back from the person who got it; deleting an item (×) has no confirmation: a toast with an Undo button (5 s, `deleteItem` in `app.js`, one offer at a time) puts it back through `store.restore`, which re-creates the item under the same id with its old data (number, ean, amount, state, authorship) and gives the point back to the person it was taken from, so the score ends where it was and nothing counts twice (`restore` is a queueable outbox op like the others); equal points share the same place. "New round" (`resetScores`) just sets every counter to zero: nothing already in the basket is credited to anyone, and counters never go below zero.
- App name on the home screen is "Kober" (manifest `name`/`short_name` and `apple-mobile-web-app-title`; "Kober" is a Saxon word for a basket), deliberately without "VG": the project is independent of VG Dresden, only the colours and the product data are theirs.
- Colours are the VG Dresden palette taken from vg-dresden.de (soft green #8bad73, green #669c03, light greens #e8edde/#d4dac8, orange #f7a642). They live in one place, `public/theme.css` (CSS variables, light and dark, each with a comment), which `index.html`, `privacy.html` and `docs/index.html` link before their own styles: the three pages no longer need manual sync and must not define palette variables themselves. Loose colours (toast, scrim, shadows, scanner, QR background, DEV tag, phone frame in the help page) are tokens there too; do not hard-code a colour in a page, add a token. The dev site uses the same palette (there is no dev colour override any more; `dev-theme.css` is gone and a test keeps it gone): only the "DEV" tag next to the fox and the blue dev app icon tell them apart. What CSS cannot reach (theme-color metas, manifest colours) is the release value in both builds; `scripts/build-site.mjs` only changes the manifest name and icons for dev. `test/theme.test.js` guards this structure (every `var(--x)` is defined, light and dark blocks match, `sw.js` precaches the file, no second palette). Filled buttons use the soft green (`--fill`, #8bad73, as on vg-dresden.de) with dark `--on-fill` text for contrast. Keep light and dark values in sync inside `theme.css` (and `dev-theme.css`). One visual rule: a **filled** button (`--fill`, dark text, same soft green in light and dark mode) is an action; a switched-on toggle (the "123" number mode) is **outlined** (`.btn.sec.on`). Do not use the filled style for states.
- Layout: `#app` is a fixed shell (header, scrolling `main`, `#addBar`, tab bar). The page itself never scrolls. While the keyboard is open (`body.typing`) the shell gets the height of the visual viewport (`--app-h`) and follows its pan (`--vvtop`), so the list stays anchored at the top and loses space at the bottom. The suggestion list (`#addSuggest`) floats above the input bar (`position: absolute; bottom: 100%`) so showing it never changes the height of the bar: the input field must not move while suggestions appear. Overlays (dialogs, toast, scanner) live outside `#app` on purpose, because a transformed parent would break `position: fixed`; they take the same `--app-h`/`--vvtop` so their fields stay above the keyboard. Any text field (`focusin`) switches on the keyboard handling.
- The empty list (no item at all, open or checked off) shows a calm three-line hint (`emptyHint` in `app.js`, texts `emptyAdd/emptyShop/emptyShare/emptyHelp`, predicate `isEmptyList` in `store.js`) with a Help link; it disappears with the first item. A toast with an action (`toast(msg, {label, aria, run})`) takes clicks (`#toast.act.show{pointer-events:auto}`); plain toasts stay click-through. Small row controls (×, row ✓, row scan, `.numedit`, header buttons) get ~44px tap areas through invisible `::after` boxes without growing visibly; sideways they stop short so neighbours overlap by 4px at most.
- The toast (`#toast`) is hidden with `opacity: 0; visibility: hidden`, not by moving it off screen: a multi-line toast is taller than any fixed offset and its lower edge would peek into the page.
- Readability: text under items (`.numedit`, `.t small`) is 14px, tab labels 14px (`clamp(12px, min(.875rem, 4.4vw), 18px)`: they follow a larger root font size only as far as the label fits its quarter of the width, so nothing is clipped; the icon sits above the label so four tabs fit at 320px; the tab bar is `min-height` 54px and may grow). Contrast limits live in `scripts/contrast.mjs` (`node scripts/contrast.mjs` prints them, `test/a11y.test.js` enforces them for light and dark): text and muted text >= 4.5:1; borders of input fields and unticked options (`--ctl-bd`), the ring of check boxes (`--tone-bd`) and the focus ring (`--focus`) >= 3:1 against both `--bg` and `--card`. A new colour pair that carries meaning goes into `PAIRS` there. Dynamic Type of iOS is not supported (all sizes are px); only the tab bar uses rem.
- Accessibility: all dialog containers get their semantics from ONE helper, `initDialogs` in `public/a11y.js` (role `dialog`, `aria-modal`, `aria-labelledby` the first visible heading or `[data-dialog-title]`, focus into the dialog on open, Tab trap, Escape clicks `.dlg-x` or `[data-dialog-close]`, focus back to the opener but never to a text field (keyboard on phones); from the "..." menu back to the menu button). It watches the class `hide`, so a dialog only has to match `DIALOG_SELECTOR` (or carry `data-dialog`) and have a heading, a close button with `.dlg-x`/`data-dialog-close`; no per-dialog code. The "..." menu: focus to the first entry on open, Up/Down/Home/End, Escape closes and returns to the button, Tab closes it. Per-item buttons carry the item name in their label (`ariaCheckItem`, `ariaBackItem`, `ariaDeleteItem`, `ariaEditNumItem`, `ariaConfirmItem`, `ariaScanItem`, empties `ariaLessItem`/`ariaMoreItem`, name through `shortName()` (40 characters) and `esc()`). `#toast` is an `aria-live` region (its text is set after it is rendered). Keyboard focus is a ring in `--focus` (`:focus` plus `:focus:not(:focus-visible)` to hide it after taps, the fallback for Safari < 15.4); do not remove outlines.
- Mobile Safari rules: `touch-action: manipulation` on everything (no double-tap zoom, pinch zoom stays for accessibility); every input needs `font-size` of at least 16px, otherwise iOS zooms into the page on focus; the shell follows the visual viewport while the keyboard is open (see Layout). None of this can be tested in the browser pane, only on a real iPhone.
- Deploys: GitHub Pages sends `max-age=600`, so `sw.js` fetches own files with `cache: 'no-cache'` to show a new version right after a reload. Still bump `VERSION` in `public/sw.js` when files change.
- Everything read from the database is untrusted: **escape it with `esc()` before it goes into HTML** (titles, user keys, ids, numbers). User keys are `"<emoji> <name>"` and are sanitised by `userKey()` in `store.js`; keep `store.js` validation in line with `database.rules.json`.
- The Firebase web config in `public/firebase-config.js` is public by design (allow-listed in `.gitleaks.toml`). Access control is the rules file plus the list code.
- The VG endpoints are public and send CORS `*` when the browser sends an `Origin` header (plain `curl` hides this); see `docs/vg-api.md`. Do not call the write endpoints (`shareList.php`, `sendFeedback.php`).

## Release and dev site

One GitHub Pages site shows two versions (`.github/workflows/pages.yml`, `scripts/build-site.mjs`): the **root is the latest release** (the newest tag `v*`; until the first tag exists it is main), **`/dev/` is the current main**. Work and push to main as usual: only `/dev/` changes. A release is cut by the user's word: `gh release create vX.Y.Z --target main --notes-file …` (or `git tag` + push), then `gh workflow run pages.yml --ref main` publishes it (a run started by the tag itself is rejected: the environment github-pages only accepts the branch main). Check the run, then the live site. Never tag on your own.

- The dev copy is its own app. `public/env.js` derives `IS_DEV` from the path and `NS`, a prefix for **every** localStorage key (`LS` in `app.js`, the local database in `store.js`, the VG cache in `vg.js`) and for the service worker's cache names, because both sites share one origin. A new storage key or cache must use `NS`, otherwise a dev build can damage the data of the release.
- It has the same colours as the release and is told apart by the "DEV" tag next to the fox and by its own blue app icon (`public/icons/dev-*.png` from `npm run icons`); `build-site.mjs` gives it its own manifest name, so both can sit on one home screen.
- Firebase: dev uses its **own Firebase project** (the projects keep their old ids `vg-korbjagd` and `vg-korbjagd-dev` from the former name Korbjagd) through `public/firebase-config.dev.js` (the build copies it over `firebase-config.js` in `/dev/`). `export default null;` means demo mode (shared lists live in the browser only). Never point dev at the production database. The rules in `database.rules.json` are published by hand to both projects, dev first.
- Gotcha: the production service worker also covers `/dev/` until the dev worker takes over on the first visit; harmless, the dev worker has its own caches.

## Name matching review (periodic, by an agent)

**Principle: usable beats perfect.** The check is there for a clear slip (an apple item with the number of an orange), not to police every pair. Most of the time the right number is typed anyway, so the app should ask only when it is quite sure that the number is wrong. A few wrong accepts (Tomaten ~ Tomatenmark) are fine; every needless question is worse. So when reviewing, close gaps where the same product is questioned, and do not tighten the threshold to catch borderline pairs.

The name check and the synonym lists in `public/vg.js` need a look every few months and whenever someone reports a pair that was questioned although it is the same product. It takes judgement (which words name the same product), so it is a job for a capable agent on request, **not** for a GitHub Action: a script can only report candidates.

1. `npm run matching:check` (`scripts/check-matching.mjs`) downloads the VG product list (read-only) and holds the everyday items of `scripts/fixtures/typical-items.txt` against it. It lists items with nothing in the VG list (information only) and "near misses": VG names with the same word start that the name check would question.
2. Read the near misses and decide each one. Same product in other words (Möhren ~ Bundmöhren, Walnüsse ~ Walnusskerne): extend a group in `SYNONYM_GROUPS`, or add a word to `COLLECTIVES` when the plain word fits every compound ending in it (Brot, Brötchen). Different product (Apfel vs Apfelsaft, Tomaten vs Tomatenmark): leave it.
3. Record the decision as a checked pair in `scripts/fixtures/typical-items.txt`: `Item => VG name` (must be accepted) or `Item != VG name` (must stay questioned). `test/matching.test.js` runs them all, `test/vg.test.js` guards the groups (no word in two groups).
4. Look at the VG list itself too: frequent words that no everyday item covers yet. Add the new everyday items to the list.
5. `npm test`, bump `VERSION` in `public/sw.js`, commit, push (after the user's yes).

`npm run matching:off` (`scripts/check-off-synonyms.mjs`) is a second source of candidates: it downloads the German synonym sets of the Open Food Facts ingredient taxonomy (ODbL) into memory and lists the pairs the name check would question. Nothing from it is stored in the repo or bundled into the app; each candidate is judged by hand like the others. OpenThesaurus (German synonyms, CC BY-SA 4.0 or LGPL 2.1, attribution needed) is another place to look words up, also not bundled.

## Commands

```bash
npm test                                             # node --test
npm run test:screens                                 # layout check at small phone sizes (needs Chrome; not part of npm test or prek)
python3 -m http.server 3100 --directory public       # serve the app (port 3000 may be taken by another session)
```

Checks: prek (`prek.toml`: file hygiene, JSON/YAML, `node --check`, tests, gitleaks) locally, and the same in GitHub Actions through **autofix.ci** (`.github/workflows/autofix.yml`, the maintainer's decision): one prek job, gitleaks included, no separate gitleaks job. autofix.ci commits what the fixing hooks repair (whitespace, end of files) back to the branch, so after a push to `main` run `git pull --rebase` before the next commit if the bot added a commit. What a fixer cannot repair (tests, secrets, JSON/YAML) still fails the run. The workflow must keep the name `autofix.ci` and the GitHub app *autofix.ci* must stay installed. The config is `prek.toml` (prek's native format, converted with `prek util yaml-to-toml`). The hooks that are not built in use prek's own toolchain (`language = "node"` for `node --check` and `node --test`) instead of tools that happen to be installed (`language = "system"`). **gitleaks is the standard hook and scans only staged changes, always** (the maintainer's decision: no whole-tree or history scan, no extra hook for it); in CI, where nothing is staged, it therefore finds nothing, and the commit-time check is what counts. `pages.yml` tests and deploys `public/`. Dependabot (`.github/dependabot.yml`) opens a weekly pull request for new versions of the GitHub Actions in the workflows; the maintainer merges it (check that the checks are green). It does not cover the hook revisions in `prek.toml`: `prek autoupdate` does, now and then.

## Testing notes

- With an empty `firebase-config.js` (`export default null`) the app runs in a demo mode that stores shared lists in the browser as well.
- Testing against the real Firebase project creates lists that the hardened rules do not let clients delete. Prefer demo mode or the unit tests; clean up leftovers in the Firebase console.
- Overload handling (`conn.js`, `sim.js`): the connection state (ok, connecting, degraded, busy) drives the `#connBanner` bar on shared lists; the local list never shows it. `?sim=overload|slow|flap|recover:<seconds>|cut:<seconds>[:<back>]` swaps the shared-list backend for a simulated server with fault injection (`sim.js`); it works only in demo mode or on the dev site, never on the release with a real database. Tests use the same sim with a manual clock (`test/overload.test.js`). Stage 2 keeps changes across reloads: `outbox.js` writes the INTENT of every item and empties operation (`add`, `check`, `setNum`, `setEan`, `remove`, `depositAdd`, `depositRemove`; never create/exists/deleteList/shareLocalList/joinShared) to localStorage (`NS + 'kober-outbox'`, `{id, code, op, args, ts}`) before it is tried, and strikes it out when the store call resolved. While the state is degraded or busy nothing is sent (the entry just waits); when it is `ok` again, and on start, the entries of the open list are replayed in order through the same store methods (`store.flush(code)`, called from the conn subscription in `app.js`). Replay relies on the store methods aborting when the target state already matches; the point after an item change is journaled as its own `bump` entry the moment the item transaction commits (`point` in `store.js`), so a reload in between neither loses nor doubles it. Every entry is validated again (localStorage is user-writable), max 200 entries (oldest dropped, toast `outboxFull` once), entries older than 24 h are dropped. Known and accepted: a replayed `add` of an item somebody deleted meanwhile reappears, a replayed `check` overrides a later change of another person (last writer wins), a replayed `depositAdd` counts twice only if the page died between commit and strike-out, two tabs would both replay. The view applies waiting entries on top of the last snapshot at once (`outbox.overlayFor` in `render()`: check marks flip, items appear; points are never shown ahead); a live snapshot is authoritative. `cache.js` keeps the last live snapshot per list (`NS + 'kober-cache:' + code`, last 3 lists, at most 200 KB each, sanitised on load) and shows it read-only (`stale`: writes are refused with a toast) on a first load until live data arrives. The banner adds `connPending` and the ranking tab shows `connScoreLater` while degraded or busy and the outbox is not empty. Tests: `test/outbox.test.js`. Not covered: a first load where the SDK itself cannot be fetched (offline, no browser cache) still falls back to the local list without the cached shared list. The Firebase SDK itself cannot be driven into a real connection limit from a test: that part only shows on a real project.
- Browser-pane checks: emulate a 375px viewport; the on-screen keyboard and service workers cannot be tested there.
- **Old phones (iPhone SE 1st generation: 320x568 CSS px, last system iOS 15.8, Safari 15).** Two checks keep the app usable there. `test/compat.test.js` (in `npm test` and prek) scans `public/` (not `vendor/`) for JS/CSS features that Safari 15 lacks (deny-list with the first Safari version per entry; `dvh`, `:has()`, `color-mix()`, `AbortSignal.timeout`, lookbehind regexes, `structuredClone`, `.at()` ...). A use that has a fallback or degrades quietly carries `compat-ok: <reason>` in a comment on the same line; a marker without a match fails the test. Prefer the fallback over the marker: before `dvh` give the rule a size that works without it (the shell and dialogs also have `bottom:0` for that reason), wrap `color-mix()` in `@supports`, feature-detect JS APIs. The Firebase SDK major is pinned in the test (10.x lists Safari 11+); check Firebase's supported environments before moving to another major.
- `npm run test:screens` (`scripts/check-small-screens.mjs`, playwright-core with Chrome like the screenshot script, demo mode, VG fixtures; `--only=320x568`, `--lang=de`, `--scheme=dark`, `--shots=/tmp/x` for a screenshot of every screen; about 5 minutes for everything) drives every screen at 320x568, 320x480 (approximates the keyboard being open: the real keyboard and its pan cannot be reproduced in a desktop browser), 375x667 and 390x844, in German and English, light and dark, and fails on horizontal overflow, elements wider than the screen, truncated button text or placeholders, controls outside the screen or overlapping, inputs below 16px, dialogs that neither fit nor scroll, and **tap areas below 40x40 px**. The tap area is measured as a finger meets it: `document.elementFromPoint` along the centre lines of the control, so pseudo-element hit areas (`.chk::after`, `.rowbtn::after`, `.numedit::after`) count and a neighbour that covers part of them counts against it (keep a 10px gap between small buttons). Only exception: a link inside a sentence. Run it after layout or CSS changes and before a release; it only knows the screens listed in the script, so add a step when a new screen or dialog appears. Narrow phones (`max-width:369px`): the number field of a list row wraps under the title; the input bar and the tab bar get tighter. What a desktop browser cannot show: the real keyboard, safe areas, Safari 15 rendering itself.
