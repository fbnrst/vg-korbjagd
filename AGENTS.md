# AGENTS.md

Guidance for AI agents and humans working on **vg-korbjagd**: a shared shopping list PWA with a game (leaderboard), independent of VG Dresden but using its public product data.

## Language rules

- **Source code is English**: identifiers, comments, test names, error/log messages, config comments, workflow step names.
- **The web app UI is localised**: it follows the system language, German or English (English is the fallback). All user-visible text lives in `public/i18n.js` (`STRINGS.en` and `STRINGS.de`, keys must exist in both). Do not hard-code UI text in `app.js`; static texts in `index.html` have English defaults that `applyStatic()` replaces. Use `t('key', { param })`. Never name a loop variable `t` in `app.js` (it shadows the translation function). `?lang=de|en` overrides the language for testing.
- Documentation: `README.md` is English. `docs/*.md` are currently German and stay German unless asked otherwise. The end-user help page (`public/docs/index.html`) and the privacy notice (`public/privacy.html`) are bilingual and follow the same language detection.
- Data coming from the VG servers (product and deposit names) stays German.

## Layout

- `public/` is the whole app (static, ES modules, no build). Served by GitHub Pages.
  - `app.js` UI and flows, `store.js` data layer, `vg.js` VG data/import, `i18n.js` texts, `sw.js` service worker, `legal-config.js` contact for the privacy page.
  - `privacy.html`, `docs/index.html` (help page for end users), `vendor/` (third-party, MIT, excluded from checks).
- Help page screenshots (`public/docs/img/<lang>-<scene>.jpg`) are built **locally and only when the user explicitly asks for it** (not in CI, not automatically after UI changes). The agent runs `npm run docs:screenshots` (`scripts/docs-screenshots.mjs`: `playwright-core` with the installed Chrome or `CHROME_PATH`, the real app in demo mode with Firebase off, invented VG demo data from `scripts/fixtures/vg/`, 375px, German and English). **Every generated image must be looked at (Read tool) before it is committed**: no cut-off or overlapping text, no toast or demo banner, no half-rendered state, the right language, the current UI (new buttons, colours). If something is off, fix the script or the app and render again. `npm run docs:screenshots -- /tmp/shots` previews without touching the repo. **Order of work: screenshots come last.** Implement everything else first (code, texts, docs, tests), commit and push that, and only then render, check and commit the images, followed by a second push. Rendering earlier wastes work because every further UI change makes the images stale again. The images are not refreshed by UI changes on their own: when a change is visible in a screenshot scene, tell the user and offer to regenerate.
- `scripts/` maintenance scripts: `cleanup-lists.mjs` (cleanup of old lists), `make-icons.mjs` (`npm run icons`: draws the app icon, a fox face on the VG green, and renders `public/icon.svg`, `public/logo.svg` and `public/icons/*.png` with Chrome; bump `VERSION` in `public/sw.js` afterwards). `database.rules.json` Firebase Realtime Database rules (**published by hand in the Firebase console**, see `docs/security.md`).
- `test/` Node tests (`node --test`, no dependencies). `docs/` developer docs.

## Behaviour that must stay true

- **Local first**: the list lives in `localStorage` under the list code `LOCAL` (no name, no server, works offline). The leaderboard/game only exists for shared lists. Sharing uploads the local list (`store.importList`, no points are awarded for existing items) and removes the local copy; the header has share and a "…" menu (reset list: a dialog to remove checked-off items or all items, optionally empties, with a note that it applies to everyone on a shared list; import list (from the VG app); "Join list" on the local list only; "Leave list" on shared lists only; help; privacy). The ranking tab has "Change name" (name and emoji; `store.renameUser` moves points, empties and marks to the new key). Player emojis (`EMOJIS` in `app.js`) are single code points, because joined sequences render differently across phones. There is no title and no counter in the header, only the fox logo (`logo.svg`, the fox without the green tile) on the left.
- Shared lists can be deleted by any member ("Delete this list for everyone", `store.deleteList`; the rules allow writes at list level only for deleting) and expire after 30 days without activity: `store.js` stamps `activity` (at most hourly; opening or changing counts) and `.github/workflows/cleanup.yml` runs `scripts/cleanup-lists.mjs` weekly (needs the secret `FIREBASE_SERVICE_ACCOUNT`, see `docs/retention.md`). A client that sees its shared list disappear falls back to the local list.
- Scanned codes: VG shelf labels carry the VG number (`vgNumFromCode` in `vg.js`: QR "VG n …", 8 digits -> digits 4-7, 13 digits -> first 12); other EANs go to Open Food Facts. The row scan button (next to each number field) sets the number or remembers the EAN on that item and asks first if the names differ. Typed numbers are checked the same way (`numberFits` in `app.js`; placeholder products are exempt). `similarNames` in `vg.js` is graded: the best word pair by Dice coefficient of letter pairs must reach `SIMILAR_ENOUGH` (0.75), generic words like "Bio" and colours (rot, grün, weiß …) are ignored, words under four letters must match exactly, so Tomate/Tomaten and Äpfel/Apfel Elstar pass while Apfel/Orange and Apfel/Apfelsaft are questioned. Listed synonyms (`SYNONYM_GROUPS` in `vg.js`, e.g. Porree/Lauch, Möhre/Karotte) count as identical: add a group whenever a shopper's word is questioned although it names the same product. Collective words (`COLLECTIVES`, now only "Brot") match every compound that ends in them, so "Brot" fits any bread while Roggenbrot vs Dinkelbrot stays questioned. A word may sit in one group only (a test checks it, the later group would silently win), and a group must not swallow a different product (Apfel vs Apfelsaft, Salat vs Feldsalat stay questioned). The groups were extended against the whole VG product list (about 7100 real products): vegetable sorts, nut kernels, raisins, jam. A number the database lists as unused ("unbesetzt", `p.placeholder`) is always confirmed before it is accepted, in the input bar, on rows and in the scanner. Opening the scanner, a dialog or a menu first dismisses the keyboard (`dismissKeyboard` in `app.js`). Typing in the manual field of the scanner dialog switches the camera off (`stopCamera`, class `manual` on `#scanner`) and emptying it starts the camera again. The manual field in the scanner dialog takes 1-7 digits (a VG number, with suggestions from 3 digits) or 8-14 digits (a barcode number). Number fields have a visible confirm button because the iPhone number pad has no Return key; the add "+" and the confirm buttons are disabled (muted) until there is something to submit.
- Checkout shows only items with a VG number. Typing three or more digits (numbers) or two or more letters (names) shows a tappable list of matching products (tap = add). Names are de-duplicated and always added without a number; the number can be added or changed on the list (small number under an item, empty field removes it). Placeholder products ("unbesetzt …", "RESERVIERT …", about a fifth of the VG list) are never suggested (`vg.js`), but a fully typed placeholder number is still accepted and the item takes the placeholder title.
- Points: +1 for checking off an item (or entering its VG number in the "No." field) and +1 per empties piece; un-checking or deleting takes the point back from the person who got it; equal points share the same place. "New round" (`resetScores`) just sets every counter to zero: nothing already in the basket is credited to anyone, and counters never go below zero.
- App name on the home screen is "Korbjagd" (manifest `name`/`short_name` and `apple-mobile-web-app-title`), deliberately without "VG": the project is independent of VG Dresden, only the colours and the product data are theirs.
- Colours are the VG Dresden palette taken from vg-dresden.de (soft green #8bad73, green #669c03, light greens #e8edde/#d4dac8, orange #f7a642). They live as CSS variables at the top of `public/index.html`, `privacy.html` and `docs/index.html`; filled buttons use a darker green and `--on-green` text for contrast. Keep light and dark values in sync. One visual rule: a **filled** button (`--fill`, white text, same dark green in light and dark mode) is an action; a switched-on toggle (the "123" number mode) is **outlined** (`.btn.sec.on`). Do not use the filled style for states.
- Layout: `#app` is a fixed shell (header, scrolling `main`, `#addBar`, tab bar). The page itself never scrolls. While the keyboard is open (`body.typing`) the shell gets the height of the visual viewport (`--app-h`) and follows its pan (`--vvtop`), so the list stays anchored at the top and loses space at the bottom. The suggestion list (`#addSuggest`) floats above the input bar (`position: absolute; bottom: 100%`) so showing it never changes the height of the bar: the input field must not move while suggestions appear. Overlays (dialogs, toast, scanner) live outside `#app` on purpose, because a transformed parent would break `position: fixed`; they take the same `--app-h`/`--vvtop` so their fields stay above the keyboard. Any text field (`focusin`) switches on the keyboard handling.
- The toast (`#toast`) is hidden with `opacity: 0; visibility: hidden`, not by moving it off screen: a multi-line toast is taller than any fixed offset and its lower edge would peek into the page.
- Mobile Safari rules: `touch-action: manipulation` on everything (no double-tap zoom, pinch zoom stays for accessibility); every input needs `font-size` of at least 16px, otherwise iOS zooms into the page on focus; the shell follows the visual viewport while the keyboard is open (see Layout). None of this can be tested in the browser pane, only on a real iPhone.
- Deploys: GitHub Pages sends `max-age=600`, so `sw.js` fetches own files with `cache: 'no-cache'` to show a new version right after a reload. Still bump `VERSION` in `public/sw.js` when files change.
- Everything read from the database is untrusted: **escape it with `esc()` before it goes into HTML** (titles, user keys, ids, numbers). User keys are `"<emoji> <name>"` and are sanitised by `userKey()` in `store.js`; keep `store.js` validation in line with `database.rules.json`.
- The Firebase web config in `public/firebase-config.js` is public by design (allow-listed in `.gitleaks.toml`). Access control is the rules file plus the list code.
- The VG endpoints are public and send CORS `*` when the browser sends an `Origin` header (plain `curl` hides this); see `docs/vg-api.md`. Do not call the write endpoints (`shareList.php`, `sendFeedback.php`).

## Commands

```bash
npm test                                             # node --test
python3 -m http.server 3100 --directory public       # serve the app (port 3000 may be taken by another session)
prek run --all-files                                 # all checks (installed as git hook via `prek install`)
```

Checks: prek (`.pre-commit-config.yaml`: file hygiene, JSON/YAML, `node --check`, tests, gitleaks) locally, the same in GitHub Actions (`.github/workflows/checks.yml`, plus a full-history gitleaks scan). `pages.yml` tests and deploys `public/`.

## Testing notes

- With an empty `firebase-config.js` (`export default null`) the app runs in a demo mode that stores shared lists in the browser as well.
- Testing against the real Firebase project creates lists that the hardened rules do not let clients delete. Prefer demo mode or the unit tests; clean up leftovers in the Firebase console.
- Browser-pane checks: emulate a 375px viewport; the on-screen keyboard and service workers cannot be tested there.
